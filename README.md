# docdb-perf-tools

Utilities for running MongoDB-compatible DocumentDB performance benchmarks. The
main workload runner is `benchly`, a Rust binary under `src/benchly`, with
PowerShell wrapper scripts for common read, write, find, and update benchmark sweeps.

## Recommended Setup

Use a dedicated Ubuntu machine for benchmark runs. A shared workstation or host
with other active services can add CPU, memory, disk, and network noise that
makes results harder to compare.

Recommended machine characteristics:

- Fresh Ubuntu VM or physical machine with `sudo` access.
- No unrelated workloads running during the benchmark window.
- Network placement close to the target database, ideally in the same region or
  private network path when possible.
- Enough CPU and network headroom to drive the largest worker counts in the
  sweep. The default wrappers test `8, 24, 48, 64, 128, 256` workers.
- A dedicated test database or collection. The benchmark wrappers may drop and
  recreate benchmark collections unless you pass options such as `-SkipPreload`.

## Setup

From the repository root:

```bash
cd docdb-perf-tools
chmod +x scripts/install-pre-reqs.sh scripts/install-rust.sh
./scripts/install-pre-reqs.sh
./scripts/install-rust.sh
source "$HOME/.cargo/env"
```

`install-pre-reqs.sh` installs build tools, `make`, PowerShell, and the PostgreSQL
client tools (`psql` and `pgbench`). `install-rust.sh` installs Rust through
`rustup`; accept the default Rust install unless you have a specific local
policy.

## Connection Secret

Do not pass the connection string directly on the command line. Copy it into a
local secret file and pass that file to the benchmark scripts with
`-MongoDbUrlFile`.

If you already have the connection string in a secure local file:

```bash
cp /path/to/mongodb-url.secret ./local.secret
chmod 600 ./local.secret
```

Or create the file manually:

```bash
printf '%s\n' '<mongodb-or-documentdb-connection-string>' > ./local.secret
chmod 600 ./local.secret
```

The secret file should contain only the connection string, with no quotes or JSON
wrapper. Files such as `*.secret`, `*.secret.*`, `.env`, and the `secrets/`
directory are ignored by this repo, but still avoid committing or sharing them.

## Build

Build the release binary before running benchmark sweeps:

```bash
make
```

This builds `src/benchly/target/release/benchly`.

## Docker

Build the Docker image without running a benchmark:

```bash
./scripts/docker-build-run.sh --build-only
```

Build the image and run Benchly in a container. The helper mounts the secret file
read-only and writes reports to `bench-results/` on the host:

```bash
./scripts/docker-build-run.sh \
  --mongodb-url-file ./local.secret \
  --test write \
  --workers 8 \
  --duration 120 \
  --run-label docker_write_smoke
```

Use `--skip-build` to reuse an existing `benchly:local` image, `--output-dir` to
choose a different host results directory, or `--dry-run` to preview the Docker
commands. Arguments that are not Docker helper options are passed through to
`benchly`.

## Run Benchmarks

From the `scripts` directory, pass the secret file explicitly:

```bash
cd scripts
./run-read-bench.ps1 -MongoDbUrlFile ../local.secret
./run-write-bench.ps1 -MongoDbUrlFile ../local.secret
./run-find-bench.ps1 -MongoDbUrlFile ../local.secret
./run-update-bench.ps1 -MongoDbUrlFile ../local.secret
./run-find-and-update-bench.ps1 -MongoDbUrlFile ../local.secret
```

You can also run the wrappers from the repository root:

```bash
./scripts/run-read-bench.ps1 -MongoDbUrlFile ./local.secret
./scripts/run-write-bench.ps1 -MongoDbUrlFile ./local.secret
./scripts/run-find-bench.ps1 -MongoDbUrlFile ./local.secret
./scripts/run-update-bench.ps1 -MongoDbUrlFile ./local.secret
./scripts/run-find-and-update-bench.ps1 -MongoDbUrlFile ./local.secret
```

To preload the same dataset used by `Load-Test-cs.ps1` without starting a
benchmark, run:

```powershell
./Preload-Data.ps1
```

This recreates `benchmark_db.benchly_test` with 2,000,000 1 KB documents and
verifies the resulting document count. Override the defaults when needed:

```powershell
./Preload-Data.ps1 `
  -MongoDbUrlFile ./secrets/onebox_m40.secret `
  -Database benchmark_db `
  -Collection benchly_test `
  -PreloadCount 2000000 `
  -DocSize 1024
```

To benchmark gateway point reads against that preloaded dataset, configure the
PostgreSQL endpoint through the standard libpq environment variables:

```powershell
$env:PGHOST = "<postgres-host>"
$env:PGPORT = "5432"
$env:PGDATABASE = "<postgres-database-containing-the-extensions>"
$env:PGUSER = "<postgres-connection-user>"
./benchmark_gateway_point_reads.ps1
```

The defaults target `benchmark_db.benchly_test` and all 2,000,000 IDs generated by
`Preload-Data.ps1`. The PostgreSQL database in `PGDATABASE` is the physical
database containing the extensions; `-LogicalDatabase` is the logical document
database. The benchmark automatically uses the active PostgreSQL `current_user`
as the dispatch role. Use `-LogicalDatabase`, `-Collection`, and
`-DocumentCount` together when overriding the preload defaults.

To benchmark the same preloaded `benchmark_db.benchly_test` dataset through the
original `mongo_api_v1.find_cursor_first_page` path, run:

```bash
./point_reads_original.sh
```

This uses the same database, collection, 2,000,000-document count, and string
`doc_...` identifiers as `Preload-Data.ps1`.

To exercise point reads through the MongoDB gateway with Benchly, using the
worker-sweep pattern from `Load-Test_v2.ps1`, run:

```powershell
./Load-Test-PointReads.ps1
# Override the gateway connection or match a custom preload:
./Load-Test-PointReads.ps1 -MongoDbUrlFile ./local.secret `
  -Database benchmark_db -Collection benchly_test -PreloadCount 10000 `
  -Workers 1,2,4,8 -Duration 45 -SkipBuild `
  --set cluster.type=gateway --set cluster.size=m40 --set cluster.version="your-version"
```

This uses `run-read-bench.ps1 -Driver benchly -SkipPreload` to run `_id` point
reads against the existing dataset, without dropping or preloading it. Defaults
match `Preload-Data.ps1`: the connection file `secrets/1103_m40.secret`,
`benchmark_db.benchly_test`, 2,000,000 documents, and 1 KB document size.
The sweep runs 1, 2, 4, 8, 12, 16, 24, and 32 workers for 45 seconds each and
tags related reports with `run.group`. The connection file must target the
MongoDB gateway; no PostgreSQL connection is used. This is the existing Benchly
point-read benchmark, not an exhaustive document-content validator.

For single-document inserts with a timeout sent to the MongoDB gateway, run:

```powershell
./Load-Test-PointInserts.ps1 -InsertMaxTimeMs 5000 -InsertTimeoutMs 10000 `
  -MongoDbUrlFile ./secrets/1103_m30.secret -Workers 256 -Duration 45 `
  -ClusterType rust_v1_baseline -ClusterVersion "v2.2.0-505c9b0b0a" -ClusterSize m30
```

This follows the `Load-Test_1103.ps1` pattern: 1 KB documents, 256 workers,
45-second runs, cluster metadata, and automatic `run.group`. There are two
independent limits, both applying to worker warmup and measured point inserts:

| Parameter | Script default | Behavior |
| --- | --- | --- |
| `-InsertMaxTimeMs` | `5000` | Sends `maxTimeMS: 5000` in the BSON insert command over the MongoDB wire protocol. `0` omits the field and retains the native driver insert path. |
| `-InsertTimeoutMs` | `5000` | Local client deadline; not sent over the wire. Set it higher than the server limit to allow time for connection setup and the server response. |

Neither is the total benchmark duration. The script uses the dedicated
`benchmark_db.benchly_point_inserts` collection, which is **dropped and recreated
for each worker-count run by default**. Do not change it to your preloaded read
collection unless you explicitly want to add more documents to it.

To keep the existing collection and append inserts instead:

```powershell
./Load-Test-PointInserts.ps1 -NoDropCollection
# -SkipPreload is an equivalent option, matching the other benchmark wrappers.
```

No-drop mode preserves existing documents and indexes across all worker-count
runs. New inserts use unique string IDs (`doc_` plus an ObjectId's hexadecimal
value) so repeated runs do not restart at `doc_000000000000` and hit duplicate
keys. The default drop/recreate and preload paths keep their sequential ID
format. In no-drop mode `-Indexed` adds the indexed field to new documents but
does not create an index; any desired index must already exist.

The client deadline includes server selection, connection-pool wait, and awaiting the
insert response. It excludes document generation, initial connection checks,
collection/index setup, and rate-limit sleeps. Insert timeouts are logged and
counted as failures during measurement, not successful inserts. Workers continue
with new documents for the configured duration, even with `--stop-on-failure`;
timeouts alone do not fail the run or stop the worker-count sweep. Warmup
timeouts are logged and do not prevent measurement from starting (warmup is
excluded from report counts). Non-timeout errors still stop the run and exit
nonzero with the wrappers' `--stop-on-failure`. Cancellation
does not guarantee server-side cancellation: the insert may still be applied.
Benchly does not retry timed-out inserts. Reports include
`benchly.insert_timeout_ms` and, when enabled, `benchly.insert_max_time_ms` in
their metadata.

The pinned MongoDB Rust driver does not expose `maxTimeMS` on `insert_one`, so
enabling `-InsertMaxTimeMs` uses an explicit, ordered, single-document `insert`
command and checks write errors and acknowledgement counts. Configured write
concern is preserved; `w=0` is rejected. This is not `writeConcern.wtimeout`,
which limits the wait for write-concern acknowledgement, not command execution.
The gateway must support and honor `maxTimeMS`; sending the field alone cannot
prove enforcement. Unsupported-option errors are surfaced without silently
retrying without the timeout. See the [MongoDB insert command documentation](https://www.mongodb.com/docs/manual/reference/command/insert/).

The existing write wrapper also accepts both options, defaulting to `0` (off).
`-InsertMaxTimeMs` requires point inserts (`-BatchSize 0` or `1`); larger batches
are explicitly rejected in this mode. With `-BatchSize` greater than 1,
`-InsertTimeoutMs` alone covers the entire `insert_many` call. Existing wrapper
invocations without these options retain their driver-configured timeout
behavior. Rebuild Benchly before using the options; do not use `-SkipBuild` with
an older binary.

The default benchmark sweep runs each workload at `8, 24, 48, 64, 128, 256`
workers, with 1 KB documents, a 5 second warmup, a 300 second measurement window,
and a 15 second pause between worker counts.

## Common Parameters

The read, write, find, update, and find-and-update wrappers share these parameters:

| Parameter | Default | Description |
| --- | --- | --- |
| `-MongoDbUrlFile` | Required | Path to a file containing the connection string. |
| `-Database` | `benchmark_db` | Database used for the run. |
| `-Collection` | `benchly_test` | Collection used for the run. |
| `-Workers` | `8,24,48,64,128,256` | Worker counts to sweep. Pass comma-separated values or repeated values. |
| `-DocSize` | `1024` | Document size in bytes. |
| `-Duration` | `300` | Measurement duration in seconds for each worker count. |
| `-Warmup` | `5` | Warmup period in seconds before measurements are recorded. |
| `-OutputDir` | `../bench-results` | Directory where benchmark reports are written. |
| `-Indexed` | Off | Adds indexed fields and creates the supporting index. |
| `-SkipPreload` | Off | Reuses existing data and avoids dropping the collection. |
| `-SkipBuild` | Off | Skips building the Rust binary in the wrapper script. Useful after `make`. |

Read, find, update, and find-and-update workloads also support `-PreloadCount`,
which defaults to `250000`. Update and find-and-update workloads support
`-UpdateType`, which defaults to `setfield`. Find workloads support
`-FindLimit` and `-CursorBatchSize`. Write workloads support `-BatchSize` and
`-MaxWritesPerSec`, plus optional `-InsertTimeoutMs` (client deadline) and
`-InsertMaxTimeMs` (wire `maxTimeMS`, point inserts only). Both use milliseconds;
`0` in the wrappers omits the corresponding limit.

Examples:

```bash
./scripts/run-read-bench.ps1 \
  -MongoDbUrlFile ./local.secret \
  -Workers 8,24,48 \
  -Duration 120 \
  -RunLabel read_smoke

./scripts/run-write-bench.ps1 \
  -MongoDbUrlFile ./local.secret \
  -Workers 64 \
  -BatchSize 100 \
  -RunLabel write_batch_100
```

Additional report metadata can be attached with `--set key=value` and is passed
through to the generated report:

```bash
./scripts/run-find-bench.ps1 \
  -MongoDbUrlFile ./local.secret \
  --set cluster=my-test-cluster \
  --set cluster.size=8 \
  --set cluster.type=standard
```

## Results

Benchmark reports are written under `bench-results/`. To produce a CSV summary
from all generated reports:

```bash
./scripts/collect-results.ps1
```

The default summary output is `bench-results/summary.csv`.

To generate dated document-size and user-sweep HTML reports directly from all
JSON reports under `bench-results/`:

```bash
./scripts/generate_reports.sh
```

Reports are written to `bench-results/reports/`. Each Python generator can also
be run without arguments to produce its corresponding dated report:

```bash
python3 ./scripts/generate_sweep_report.py
python3 ./scripts/generate_user_sweep_report.py
```

Latency charts include Mean, P50, P75, P95, and P99 series. Use the multi-select
above each latency chart to choose which series are visible.

To preview deletion of benchmark JSON reports for one cluster type:

```bash
./scripts/remove-results-by-cluster-type.ps1 \
  -ClusterType csharp_aot_baseline \
  -WhatIf
```

Remove `-WhatIf` to delete the matching `*_report.json` files after confirmation.
Use `-Confirm:$false` only when intentionally running non-interactively.

## Troubleshooting

- If `cargo` is not found after installing Rust, run `source "$HOME/.cargo/env"`
  or open a new shell.
- If a PowerShell script is not executable, run it with `pwsh`, for example
  `pwsh ./scripts/run-read-bench.ps1 -MongoDbUrlFile ./local.secret`.
- If connection attempts fail, verify the machine can reach the database endpoint
  and that the connection string in the secret file is a single non-empty line.
- Run one workload sweep at a time for cleaner measurements.
